# IINA #5909 — Scrub by Mouse Drag Mishandles Next Video

## ROOT CAUSE

`iina/PlayerCore.swift:952-963` — `PlayerCore.seek(percent:forceExact:)` clamps the requested seek percentage with `percent.clamped(to: 0..<100)`, which (per the half-open `Range` overload in `iina/Extensions.swift:412-420`) collapses any value ≥ 100 to `100.nextDown` (~99.9999999999999%). That value is so close to EOF that mpv routinely lands on the file's last keyframe, emits end-of-file, and auto-advances the playlist; nothing in the drag pipeline recognizes that the file underneath the slider has changed, so the very next drag event seeks the *new* file the same way and the advance repeats.

## CONTROL FLOW

1. **Drag begins.** The user mouseDowns on `PlaySlider`. `PlaySlider.mouseDown` (`iina/PlaySlider.swift:104-106`) just forwards to `NSSlider.super`, which kicks off standard `NSSliderCell` mouse tracking. `PlaySliderCell.startTracking` (`iina/PlaySliderCell.swift:175-183`) pauses playback and remembers the prior pause state.
2. **Drag past the right edge.** AppKit's default `NSSliderCell.continueTracking` projects the cursor position onto the slider and writes `slider.doubleValue` clamped to `[minValue, maxValue]`. Holding the cursor anywhere to the right of the slider pins `doubleValue` at `maxValue` for the entire drag.
3. **Action fires every drag tick.** AppKit invokes the slider's target/action `playSliderChanges`. `MainWindowController.playSliderChanges` (`iina/MainWindowController.swift:3246-3261`) gates on `info.state.active && info.state != .loading`, calls `super.playSliderChanges` (the seek), and then refreshes the time-preview label.
4. **Seek issued.** `PlayerWindowController.playSliderChanges` (`iina/PlayerWindowController.swift:689-692`) computes `percentage = 100 * sender.doubleValue / sender.maxValue` (= 100.0 while the mouse is past the right edge) and calls `player.seek(percent: 100.0, forceExact: !followGlobalSeekTypeWhenAdjustSlider)`.
5. **Clamp produces a near-EOF target.** `PlayerCore.seek(percent:forceExact:)` (`iina/PlayerCore.swift:952-963`) calls `percent.clamped(to: 0..<100)`. The `FloatingPoint.clamped(to: Range)` overload (`iina/Extensions.swift:413-420`) returns `range.upperBound.nextDown`, i.e. `100.nextDown`. That value is then sent to mpv via `mpv.command(.seek, args: ["\(percent)", "absolute-percent[+exact]"])`. The pre-existing comment on lines 953-955 admits this is fragile: *"mpv will play next file automatically when seek to EOF… however, it still won't work for videos with large keyframe interval."*
6. **mpv auto-advances.** mpv resolves the seek to the file's final keyframe, hits EOF, and starts the next playlist entry. While `info.state == .loading`, step 3's guard makes incoming drag actions no-ops, so loading itself is safe.
7. **Drag is still alive on the new file.** The user has not released the mouse. `updatePlayTime` (`iina/PlayerWindowController.swift:605-632`) may briefly write `playSlider.doubleValue = 0` for the freshly loaded file, but AppKit's `continueTracking` immediately overwrites it back to `maxValue` on the next drag event because the cursor is still past the slider's right edge. State leaves `.loading`, so the guard opens up.
8. **Cascade.** Steps 4-7 repeat for the new file; mpv auto-advances again; repeat for every subsequent file in the playlist for as long as the user keeps the mouse held past the right edge. One drag → many file advances.

## WHY IT CASCADES

The clamp at `PlayerCore.swift:957` was designed only to keep `percent` strictly below 100 (`100.nextDown`), not to keep the seek a *useful* distance away from EOF; the in-line comment already concedes this fails on videos with non-trivial keyframe spacing. Meanwhile, no component in the drag pipeline carries any "we just auto-advanced because the user dragged past the end of file N" state. The slider tracks raw cursor position, `playSliderChanges` recomputes a percentage from `doubleValue / maxValue` every tick, and `PlayerCore.seek` treats every call as a fresh seek into whichever file mpv currently holds — there is no notion of "this drag belongs to file N." So the moment mpv switches to file N+1, the slider, controller, and `PlayerCore` all collude to repeat exactly the same near-EOF seek on the new file, and the loop continues until the user releases the mouse. The "as if the drag delta were being applied across files" symptom is exactly this: the drag's effective coordinate is `maxValue` regardless of which file is loaded, so each file in turn is scrubbed to its own ~99.9999% mark.

## SUGGESTED FIX

The minimal, correct fix is to make `PlayerCore.seek(percent:forceExact:)` clamp to a **meaningful** safety margin from EOF rather than to `100.nextDown`. Compute the seek target in seconds and clamp against `duration` directly — e.g. `min(percent / 100 * duration, duration - 1.0)` (or some small constant tuned to typical keyframe spacing) and issue an `absolute+exact` seek — so a drag to the right edge lands inside the current file instead of on its last keyframe, and mpv never auto-advances mid-drag. A complementary defensive change is to have `PlaySliderCell.startTracking` capture the playing file's identity (e.g. playlist position or `currentURL`) and have `playSliderChanges` bail out whenever that identity no longer matches, with `stopTracking` clearing the captured identity; this guarantees that even if mpv does auto-advance, a single drag can affect at most one file. Either change on its own breaks the cascade; together they address both the proximate trigger (near-EOF clamp) and the structural gap (no per-drag file binding).

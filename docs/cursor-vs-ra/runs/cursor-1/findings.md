ROOT CAUSE: iina/PlayerCore.swift:951-963 — `PlayerCore.seek(percent:forceExact:)` clamps the slider percent in *percent* space using a half-open range `0..<100` (yielding `100.nextDown` ≈ 99.999999…%) and dispatches `absolute-percent+exact`, which the in-file comment already acknowledges "won't work for videos with large keyframe interval"; combined with `playSliderChanges` being a continuous NSSlider action that has no suppression once mpv autoadvances, every drag tick at the right edge re-fires the action against whatever file is now current and triggers another EOF roll-over.

CONTROL FLOW:
1. User mouse-drags the play knob; AppKit clamps cursor X to slider bounds, sets `playSlider.doubleValue = sender.maxValue` (100), and fires the continuous action `playSliderChanges(_:)` (base impl at iina/PlayerWindowController.swift:689-693, override at iina/MainWindowController.swift:3246-3262).
2. The handler computes `percentage = 100 * 100 / 100 = 100` and calls `player.seek(percent: 100, forceExact: !followGlobalSeekTypeWhenAdjustSlider)` (PlayerWindowController.swift:692).
3. `seek(percent:)` clamps via `percent.clamped(to: 0..<100)`. The half-open `FloatingPoint.clamped(to: Range)` overload at iina/Extensions.swift:413-421 returns `range.upperBound.nextDown` for inputs ≥ upperBound — i.e. `100.nextDown`, the largest Double less than 100.
4. `mpv.command(.seek, args: ["99.99999999999999", "absolute-percent+exact"])` is issued (PlayerCore.swift:961). For videos whose last keyframe sits well before EOF (large keyframe interval, the case explicitly called out by the existing comment at PlayerCore.swift:953-955), mpv treats this as past EOF and advances the playlist.
5. mpv emits `start-file`/`file-loaded`. `MPVController.handleEvent` sets `info.state = .starting` (iina/MPVController.swift:1142); shortly after, `PlayerCore.fileLoaded()` (PlayerCore.swift:2087-2154) sets `info.state = .loaded` and overwrites `info.videoDuration` with the new file's duration (line 2110). `updatePlayTime` (PlayerWindowController.swift:606-633) reflects the new file's small play position by setting `playSlider.doubleValue` toward 0 (line 630).
6. The user's mouse drag is still live on the same slider. AppKit's NSSlider drag-tracking re-evaluates the cursor (still past the right edge), again forces `doubleValue = 100`, and re-fires `playSliderChanges`.
7. The guard `player.info.state != .loading` in the override (MainWindowController.swift:3248) does not block: playlist-internal advance never enters `.loading` (only `openMainWindow` sets `.loading` at PlayerCore.swift:540); the path goes `.starting` → `.loaded`. State `.loaded` is `.active` and not `.loading`, so the action passes the guard.
8. `seek(percent: 100)` runs again — now against the *new* current file — clamps to `100.nextDown` again, mpv autoadvances again. Steps 5-8 repeat once per drag tick until the drag ends or the playlist is exhausted. The user perceives this as the scrubber "scrolling through" successive files.

WHY IT CASCADES:
The clamp is in the wrong unit and at the wrong layer to be a hard fence. Working in percent leaves the actual seek time at `duration * 99.999…/100`, which after mpv's keyframe rounding (or the `+exact` decode that still respects EOF) can land at or past EOF — the comment at PlayerCore.swift:953-955 admits this. Nothing downstream provides a second line of defense: `playSliderChanges` is a continuous-action handler that re-fires for every cursor-X update during the drag, no per-drag or per-file token suppresses repeat seeks once mpv has rolled over, and the only state guard in the handler (`!= .loading`) is set only by user-initiated open, not by automatic playlist advance. So each tick of a drag held past the right edge issues a fresh percent-100 seek against whatever file mpv just promoted, and each EOF roll-over feeds the next iteration. The drag delta is not being applied across files (as the bug report's mental model suggests); rather, the same percent-100 value is being re-sent against successive files because the clamp leaks once and the action loops.

SUGGESTED FIX:
Make the clamp authoritative by moving it out of percent space and into seconds. In `PlayerCore.seek(percent:forceExact:)` (iina/PlayerCore.swift:951-963), if `info.videoDuration?.second` is available and positive, compute `let seconds = min(percent * duration / 100, max(0, duration - 1.0))` (or any small epsilon below `duration` that is robust to keyframe spacing) and dispatch `mpv.command(.seek, args: ["\(seconds)", useExact ? "absolute+exact" : "absolute"])` instead of percent-based mpv args. Because the resulting time is strictly less than `duration` by a margin large enough to span any reasonable keyframe interval, mpv cannot interpret the seek as past EOF, so no slider drag — no matter how long it lingers past the right edge — can trigger autoadvance, eliminating both the first advance and the cascade. (A complementary belt-and-suspenders measure is to short-circuit `playSliderChanges` when `sender.doubleValue >= sender.maxValue`, but the seconds-cap fix in `seek(percent:)` is more general and benefits every caller of the method.)

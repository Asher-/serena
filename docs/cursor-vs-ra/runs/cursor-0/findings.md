# Issue #5909 — "Scrub by Mouse Drag Mishandles Next Video"

## ROOT CAUSE
`iina/PlayerCore.swift:952-964` (`PlayerCore.seek(percent:)`) — the only safeguard against mpv auto-advancing on a near-EOF seek is `percent.clamped(to: 0..<100)`, which on `Double` yields `100.0.nextDown` (≈ 99.99999999999999%). With `absolute-percent[+exact]` mpv may still cross the file's actual EOF while resolving the seek, fire its end-of-file handling, and roll the playlist forward. Nothing in the slider drag handler detects that mpv has rolled over, so the same near-100% drag input gets applied to each successive file in turn.

## CONTROL FLOW
1. The user drags the playback slider past its right edge. `NSSliderCell.continueTracking` clamps the slider's `doubleValue` against the cell's `minValue=0 / maxValue=100` (set in `PlaySliderCell.awakeFromNib`, `iina/PlaySliderCell.swift:39-41`), so `doubleValue` saturates at 100.
2. NSSlider continuous tracking fires the `@IBAction` `MainWindowController.playSliderChanges` (`iina/MainWindowController.swift:3246-3262`). The only transition guard is `guard player.info.state.active, player.info.state != .loading else { return }`, which does not exclude `.loaded` or `.playing`.
3. The override calls `super.playSliderChanges(sender)` → `PlayerWindowController.playSliderChanges` (`iina/PlayerWindowController.swift:689-693`), which computes `percentage = 100 * sender.doubleValue / sender.maxValue` (= 100.0) and calls `player.seek(percent: 100.0, forceExact: ...)`.
4. `PlayerCore.seek(percent:)` (`iina/PlayerCore.swift:952-964`) clamps via `percent.clamped(to: 0..<100)`. The `FloatingPoint.clamped(to: Range)` extension (`iina/Extensions.swift:413-421`) returns `range.upperBound.nextDown` when `self >= upperBound`, so `percent` becomes `100.0.nextDown` (~99.99999999999999%). The function issues `mpv.command(.seek, args: ["99.999...", "absolute-percent+exact"])`.
5. mpv seeks to that fraction. Per the developer's own warning comment at `PlayerCore.swift:954-956` ("it still won't work for videos with large keyframe interval"), the exact-seek decode loop can cross the file's actual EOF; mpv (default `keep-open=no`) treats this as end-of-file and advances to the next playlist entry.
6. `MPVController.handleEvent` calls `player.fileEnded(...)` then `player.fileLoaded()` for the new file (`iina/MPVController.swift:1150,1204`). `fileLoaded` (`PlayerCore.swift:2087-2154`) refreshes `info.videoDuration` and sets `info.state = .loaded`. The `.loading` window is brief and only present while mpv is opening the new entry; after that, the MainWindowController guard from step 2 stops blocking.
7. The user's drag is still active. `NSSliderCell.continueTracking` keeps mapping the mouse position (still at/past the slider's right edge) to `doubleValue = 100`. Even when `PlayerCore.updatePlayTime` (`iina/PlayerWindowController.swift:606-633`) writes the new file's near-zero position back into `playSlider.doubleValue`, the next mouse-tracking iteration overwrites it back to 100, re-firing the IBAction.
8. Steps 3–7 repeat on the freshly loaded file, cascading through the playlist until the user releases the mouse.

## WHY IT CASCADES
The codebase has exactly one defense against scrub-into-EOF — the `0..<100` percent clamp — and the developer's adjacent comment admits it is unreliable ("won't work for videos with large keyframe interval"). The clamp is also the wrong shape: it leaves an effectively zero margin (`100.0.nextDown`) on the percentage axis, which translates to less than a microsecond of headroom on a several-minute file and is much smaller than a typical keyframe interval. There is no compensating logic anywhere else: `seek(percent:)` does not consult `info.videoDuration` to apply a real seconds-based safety margin, the slider IBAction has no mid-drag awareness of file rollover (the `.loading` guard only covers a sub-frame window), and `PlaySliderCell.startTracking/stopTracking` only manipulate pause state, not the seek pipeline. So once a single near-100% drag triggers mpv to advance, the same drag input sits on top of each successive file and trips the same near-EOF auto-advance again.

## SUGGESTED FIX
Replace the brittle percent-only clamp in `PlayerCore.seek(percent:)` with a seconds-based clamp that leaves a real margin: when `info.videoDuration?.second` is known, compute `targetSec = percent / 100 * duration`, clamp it to `0...max(0, duration - margin)` for a small `margin` (e.g. 0.5–1.0 s, comfortably wider than any typical keyframe interval), and dispatch the seek using `absolute[+exact]` (against the seconds value) instead of `absolute-percent[+exact]`. That single change makes the saturated-drag input map to "near, but provably before, EOF" on every file, so each per-frame seek lands inside the current file and the cascade ends. As a defense-in-depth follow-up, `MainWindowController.playSliderChanges` could additionally early-return while `info.state == .loaded` (i.e. the just-loaded-but-not-yet-playing window after a rollover) so a stuck mouse cannot immediately reseek a freshly opened file before its first `updatePlayTime` cycle.
